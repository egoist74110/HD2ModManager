# W20 低污染双形态缓存

有效低污染仍由 `BuiltInLuaEnabled && LowPollutionMode` 决定。两种形态各生成一次后，护甲映射可以在普通和压缩形态之间来回换入。双素体回归测试中，预热之后连续五次换向，每次换入 2 个，调用编译 0 次。升级前的成品缺少实际来源载荷和游戏输入的指纹，首次应用会按当前形态建立可信记录。

## 实施计划

1. 以 Mod 根下的独立目录保存非生效形态。为已编译的成品记录来源、组件、头身、NPC、游戏输入和格式指纹，并校验成品的完整性。
2. 在托管目录事务中发布已经写完的整套生效层。映射先校验缓存并尝试换入，未命中时沿用原编译。材质刷新保持生效层结构，按实际材质输入让另一份失效。
3. 在管理器部署入口检查有效低污染模式。关闭期间只允许已经恢复的普通产物进入部署。用真实部署解析器、沙盒 Mod 和只读库体积统计核对边界。
4. 运行双向切换、局部失效、材质、删除及回滚回归，执行 Debug 构建、全量测试、Lua 回归和 master 差异检查。

## 实现和验证边界

- 当前形态放在 Mod 的 `Overwrite/`。候补形态在同一 Mod 下的 `.hd2mod-low-pollution-cache/ordinary/` 或 `compressed/`。候补层保存整套目录，包括 Unit patch、GPU 和 stream 侧车、生效材质、布局或不可压缩标记，以及编译生成的注册表、sections 和组件表。压缩形态的组件定义仍从权威来源读取，沿用原有编译格式。递归导入和副本创建跳过候补层。删除 Mod 时由现有库删除服务一起移除。[缓存实现](../../HD2ModCore/Infrastructure/Sectional/LowPollutionArtifactCache.cs)
- 编译先在同卷临时目录完成结构文件和校验值，再发布。命中时直接把完整候补目录换到 `Overwrite/`，并保留仍匹配的原生效层。目录移动出错时先让候补回原位，再恢复旧生效层。回归测试在换入后、保存原层前注入目标目录冲突，验证两份目录和原内容都恢复。操作系统若在回滚时仍持有会阻止改名的文件句柄，旧层备份可能需要人工恢复。程序被强制终止时也可能留下暂存目录或备份，这些目录不会参与常规导入和部署。[托管目录事务](../../HD2ModCore/Infrastructure/ManagedOverwriteDirectory.cs)
- 关闭低污染后，管理器部署计划会排除仍处于压缩形态的节点，直到护甲映射准备好相应普通成品。这样通过 IAS 冲突提示关内置 Lua 所触发的先行部署，也拿不到旧压缩补丁。部署继续从生效层取文件，候补层的 patch、侧车和 SEAF 原版键都在该扫描范围外。映射应用换入后会刷新节点文件事实，再部署和应用映射。回归覆盖关闭模式下的配置过滤及普通产物实际文件选择。[配置部署入口](../../HD2ModCore/Infrastructure/ProfileApplyService.cs) · [映射入口](../../HD2ModManager/ViewModels/ArmorRegistryPageViewModel.cs)
- 材质物化沿用当前 Unit 和结构，在临时目录重建完整生效层，并删除材质输入不同的候补层。回归先验证物化后普通形态仍是最新、旧候补已删除，再验证下一次压缩仅重编这一份，随后两份成品含相同的新材质 patch。重新转换调用原有编译入口，来源改变会使旧缓存失效。回归还从库删除入口移除了含候补层的 Mod。[材质物化](../../HD2ModCore/Infrastructure/OverwriteMaterializer.cs) · [回归测试](../../HD2ModCore.Tests/SectionalMergeOverflowTests.cs)

## 指纹与失效

| 项目 | 判定依据 |
| --- | --- |
| 来源结构和载荷 | 当前 sections 的结构字段、来源组件表和自定义注册表，以及编译实际选择的 Unit patch、`.gpu_resources` 和 `.stream` 的 SHA-256。sections 中记录的历史 patch 路径及快照哈希不参与，实际载荷每次都读。回归覆盖只改路径仍命中，以及保留原 sections 却改 patch 或 GPU 侧车时只重编对应素体。 |
| 组件和头身 | 按 Unit 名、section 索引规范化生效勾选，再记录头身合并开关。128 MiB 处理后采用实际编入的勾选。 |
| NPC、玩家骨架和原版 Unit | 压缩成品记录实际会生成专用 Unit 的 NPC 集合。通过编译使用的同一游戏包读取器取玩家 Avatar 和 SEAF Unit 输入字节，SEAF 还包含读取到的依赖和用于输出的条目字段。普通产物不读取这些游戏输入。回归有真实读取器搭配合成 Avatar 与原版 Unit 档案的用例。 |
| 格式与完整性 | 同时核对成品格式版本和压缩规划器版本、选中的材质 patch 与侧车，以及整套成品的文件名和内容哈希。输入不可读、成品不全或格式不兼容时走原编译。 |

## 普通用户的影响及磁盘估算

一直使用普通模式、从未生成低污染产物的素体不会留下一份候补缓存。参与低污染的自身素体在两个形态都生成后会多留一个完整生效层。无需使用 IAS 就能使用这一功能。换到游戏护甲的素体继续按现有目标规则处理。没有关联到映射的素体仍按原有范围处理，历史 SEAF 模型清理沿用原流程。

只读统计真实库 `E:\SteamLibrary\steamapps\common\HD2ModManager\mods` 的顶层 Mod 目录。以 `sectional/custom-model.json` 或 `vpk2patch/custom-model.json` 识别自定义素体，按文件逻辑长度汇总 `Overwrite/`。本次读到 26 份生效层，共 210 个文件、3,980,284,218 字节（约 3.71 GiB）。单份最大约 718 MiB。若另一形态大小相近并且全数预热，预计额外约 3.71 GiB，生效层加候补合计约 7.41 GiB。这里估算的是产物层，整个 Mod 库另有来源和材质文件。两种实际形态的几何和侧车大小会影响最终增量。

自动工具策略以 `blocked by policy` 拒绝删除本轮专用临时目录。`tmp/w20/` 中的验证日志和临时文件仍在 Git 忽略目录内。

## 用户实测步骤

1. 使用含 W20 的构建，在游戏退出时，在护甲映射关联两份自定义素体。打开内置 Lua 和低污染，点「应用」，等部署完成。旧库首次应用会为当时启用的形态建立新指纹。
2. 关闭低污染后点「应用」。该形态首次生成时，日志会写「重编素体」。重新打开并应用，再交替切两次。每轮应有对应素体的「缓存换入」日志，汇总应显示 `重编成功 0 个（尝试 0 个）`。无需改变映射即可重复应用验证「已是最新」。
3. 保持低污染设置开启，改用「启用管理器内置 Lua 类功能」总开关，重复关、开并分别应用。关闭时 `Overwrite/` 不应有压缩布局或 SEAF 专用 Unit。若设置触发的部署先于护甲映射应用，仍留有压缩生效层的节点会被暂时跳过。
4. 用可丢弃的 Mod 副本修改一个组件，或把飞船 NPC 加到一份头身合并的素体，再应用。核对只有受影响的素体重编。在详情页换材质时，对应候补形态应清理，下一次切换重新生成后应使用相同材质。删除副本后候补目录也应随 Mod 消失。
